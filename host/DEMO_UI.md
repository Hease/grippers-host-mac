# 시연 UI (세로 1080×1920) — 붙이는 방법과 아직 안 된 것

관객용 세로 화면이다. 팀원이 쓰는 `live_map.py`(가로 matplotlib 지도)를
대체하지 않고 **따로 뜬다** — 둘 중 하나만 고른다.

## 이 저장소에서 이 UI 가 건드리는 것 — 없다

`mission.py` · `navigator.py` · `vehicle_link.py` · `mission_config.py` ·
`run_sim.py` · `run_mission.py` 는 **한 줄도 안 고쳤다**(사용자 지시,
2026-09-07). 전부 읽기만 한다.

| 새로 추가한 파일 | 하는 일 |
|---|---|
| `ui/` | 화면 자체 (HTML/CSS/JS) |
| `ui_state.py` | 미션 상태 → 화면 dict. 한국어 문구·예외 코드 전부 여기 |
| `ui_bridge.py` | pywebview 창 + JS 다리 |
| `voice_input.py` | 로컬 Whisper 음성 입력 (선택) |
| `run_sim_ui.py` | 카메라·모델·차량 없이 이 UI 만 돌리는 진입점 |
| `run_mission_ui.py` | **실기용** — `run_mission.py` 에 이 UI 만 얹는다 |

`run_mission.py` 는 17줄 늘었다(`on_cycle` 훅 선언 13줄 + 호출 4줄).
기본값이 `None` 이라 **아무도 안 채우면 동작이 전과 완전히 같다** —
`python run_mission.py` 를 그냥 돌리면 이 줄들은 없는 것과 같다.

팀원 코드에서 읽어 오는 이름은 **`ui_state.py` 맨 위 "실기 FSM 결합부"
한 블록**에 모여 있다. 그쪽이 바뀌어 화면이 깨지면 고칠 곳은 거기 하나다.

## 실행

```
cd host

# 1) 하드웨어 없이 — 지금 바로 됨
../.venv/bin/python run_sim_ui.py
../.venv/bin/python run_sim_ui.py --fullscreen      # 세로 모니터 전체화면
../.venv/bin/python run_sim_ui.py --step            # 화면에서 한 단계씩
../.venv/bin/python run_sim_ui.py --speed 0.6       # 빠르게

# 2) 카메라 + 모델은 쓰고 차량은 안 씀 — model.bin 필요
../.venv/bin/python run_mission_ui.py --mock-complete

# 3) 실기 차량까지 — 사람이 지켜보는 상태에서만
../.venv/bin/python run_mission_ui.py --vehicle-ip 192.168.0.7 --ui-fullscreen
```

`run_mission.py` 의 인자는 전부 그대로 쓸 수 있다(`--cams`, `--category`,
`--seconds` …). `--no-view` 는 자동으로 붙는다 — 예전 지도(matplotlib)와
이 창은 둘 다 메인 스레드를 원해서 같이 못 뜬다.

세로 모니터가 없으면 창이 화면 높이에 맞춰 줄어든다(`ui/app.js` 의
`fitStage`, 배율 = `min(너비/432, 높이/768)`). 1080×1920 에서는 정확히
2.5배라 목업 치수가 그대로 나온다.

## ⚠️ 비상 정지는 Pi 의 하드웨어 비상정지가 아니다

화면의 "비상 정지"를 누르면 이 UI 는 **`fsm.step()` 을 건너뛰고 차량에
정지 명령만 계속 보낸다.** 그것뿐이다.

이렇게 만든 이유는 **Host 에 비상정지 경로가 아예 없기 때문**이다:

- `mission.py` 에 `request_halt()` 도 `halted` 도 없다
- `vehicle_link._STATE_TO_PI` 에 `ESTOP` 항목이 없다 — Host 가
  `MissionState.ESTOP` 을 보낸 적이 한 번도 없다는 뜻이다
  (`host/HANDOFF.md` §4 "ESTOP 경로 — Host 에 비상정지가 없다" 그대로다)

그래서 지금 이 버튼이 하는 일은 "정지 명령을 계속 보낸다"이고, **링크가
끊기면 아무 일도 안 일어난다.** Pi 쪽에는 `/mission/emergency_stop`
ROS 토픽과 자체 워치독이 따로 있는데 이 버튼은 그것을 건드리지 않는다.

**시연 전에 팀과 정할 것.** 화면에 비상정지 버튼이 있는데 실제로는 소프트
정지라는 사실을 모르는 사람이 그 버튼을 누르는 상황이 가장 위험하다.

## 명세와 실기가 다른 곳 — E-314 (파지 실패)

명세는 "3회 연속 실패하면 정지하고 사람의 선택을 기다린다"였다. 실기
FSM 은 **멈추지 않는다** — `_skip_target()` 으로 그 기물을 `skipped` 에
넣고 다음 기물로 넘어간다. 그래서 화면을 막는 카드 대신 알림 배너로
바꿨다. 카드를 띄우면 로봇은 계속 움직이는데 화면만 멈췄다고 말하게 된다.

## 복귀 정책 실험 (`--home-policy`)

실기 FSM 은 기물을 **하나 넣을 때마다** `DEFAULT_HOME_XY(0.9, 0.32)` 로
돌아간다. `mission.py` 의 RETURN_HOME 주석이 이유를 적어 두었다 — 2026-09-01
에 "포기한 뒤" 용으로 들어왔고, **2026-09-02 에 "성공한 뒤"까지 확장됐다.
그 주석에 `(시연용)` 이라고 적혀 있다.** 연출상의 결정이지 주행상 필요가
아니다.

실측하면 그 왕복이 **전체 이동거리의 45%** 다. 그래서 `mission.py` 를
고치지 않고 정책만 바꿔 끼울 수 있게 했다(`home_policy.py`).

```
python run_sim_ui.py --home-policy end     # 마지막 하나를 넣은 뒤에만 복귀
python run_sim_ui.py --home-policy never   # 투하 뒤 복귀 안 함
python run_sim_ui.py                       # always (기본, 지금 실기 그대로)
```

기물 6개 · 실기 속도 환산(전진 0.1 m/s · 회전 14.3°/s) 실측:

| 정책 | 복귀 | 주행 합계 | 기물당 | 끝난 자리 ~ 홈 |
|---|---|---|---|---|
| `always` (지금) | 6회 | 315초 | 52.4초 | 0.09 m |
| **`end`** | **1회** | **174초** | **29.0초** | **0.10 m** |
| `never` | 0회 | 150초 | 24.9초 | **1.02 m** |

`end` 가 절충점이다 — **45% 빨라지면서** 마지막에 홈으로 돌아가 연출상
"끝났습니다" 자세를 지킨다. `never` 는 조금 더 빠르지만 상자 앞에서 끝난다.

무작위 배치 3판 A/B 에서도 47% 단축(63% / 59% / 21%)으로 재현됐다.

**세 정책 모두 `_skip_target`(기물을 포기한 뒤)의 복귀는 그대로 둔다** —
그건 2026-09-01 의 원래 목적이고, 실패한 자리에 남으면 다음 탐색이 같은
기물을 또 문다.

⚠️ **실기에서 바꾸기 전에 눈으로 확인할 것**: 상자 앞에서 곧장 탐색을
시작하면 로봇이 상자를 등지고 크게 돌아야 할 수 있다. `PLACE_BACKOFF`
(투하 직후 후진)가 생긴 이유가 바로 그 접촉이다.

## 상자 침범 (`box_guard.py`) — 2026-09-07 발견 · 수정

`run_sim_ui.py` 로 6개를 옮기게 두고 로봇 중심 좌표를 매 사이클 쟀더니,
5번째 기물에서 **중심이 chess 상자 사각형 안으로 3.4cm 들어갔다**
(y=1.484, 상자 앞면 1.450). 몸통이 스친 게 아니라 차체가 상자 위로
올라선 것이다.

    #    상태             x      y     상자중심거리  부채꼴  방위
    1907 CARRY_TO_DEST  1.241  1.426    0.226      False  -153.7
    1913 CARRY_TO_DEST  1.305  1.466    0.165      False  -162.1
    1920 CARRY_TO_DEST  1.328  1.476    0.151      False  -169.8   <- 상자 안
    1954 FACE_BOX       1.344  1.460    0.165      True   -106.7

원인은 두 가지가 겹친 것이다.

1. **CARRY_TO_DEST 의 주행 목표가 원래 상자 안에 있다.** 2026-09-05부터
   `dest_xy`(y=1.30)가 아니라 INSERT 목표영역 **중심**(chess 기준
   (1.350, 1.480))을 향해 몬다 — 그 점은 앞면보다 3cm 안쪽이다.
   평소엔 접근 부채꼴이 먼저 열려 멈추는 것이지, 목표 자체가 상자 안이다.
2. **부채꼴은 남쪽 120도에서만 열린다.** 로봇이 상자 **옆**에서 다가오면
   (위 로그의 방위 −153.7 ~ −169.8도 = 서쪽 3분면) 게이트가 계속 닫혀
   있어 CARRY_TO_DEST 가 안 끝나고, 그동안 1의 목표를 향해 계속 전진한다.

`GridPathPlanner` 는 못 막는다 — 격자는 `DRIVE_AREA_Y`(상한 1.30) 안에만
있지만, 로봇이 목표 허용거리(`arrive_tol` 0.35m) 안에 들어와 탐색이 한
칸짜리가 되면 `update()` 가 **격자에 없는 원래 목표를 그대로** 부분목표로
돌려준다(navigator.py 468행). 위 로그의 "경로점 0"이 그 상태다.

`NUDGE_BOX` 의 `hard_stop`(상자 중심 반경 0.225m)도 안 걸린다 — **그
상태 안에서만** 계산되기 때문이다(mission.py 1410행). basket_target.py 의
부채꼴 주석은 *"물리적 안전은 hard_stop 이 항상 별도로 지킨다"*고 적고
있는데, CARRY_TO_DEST 에는 그 보호가 실제로는 없다. **이 한 줄이 팀원과
가장 먼저 확인할 것이다.**

### 고침

CARRY_TO_DEST 가 보는 목표의 y 만 `hard_stop` 선(1.400)으로 자른다 —
값을 내가 정하지 않고 팀원 코드가 이미 "절대 안전 반경"으로 선언해 둔
그 상수를 그대로 쓴다. `mission` 이 보는 `basket_target` 이름만 얇은
껍데기로 바꿔 끼우므로(`run_mission.signal` 과 같은 수법) 원본은 안 고치고,
**게이트 판정(`check_approach_sector`)은 안 바뀐다** — 그 함수는 자기 모듈
안에서 진짜 `target_center` 를 부르기 때문이다.

2026-09-05 에 `dest_xy` 를 안 쓰기로 한 이유("부채꼴 반경 0.15m 밖이라
게이트가 안 열린다")는 지금 없어졌다 — 그 뒤 `MAX_APPROACH_DIST_M` 이
**0.15 → 0.25** 로 커졌다. 0.18 < 0.25 이므로 상자 앞에서 정상적으로
열린다(`tests/test_box_guard.py` 가 이 전제를 못으로 박아 둔다).

### 실측 (기물 6개, 같은 배치)

| | 중심 최고 y | 앞면 침범 | 투하 | 총이동 |
|---|---|---|---|---|

`[1.265 1.250 1.261 1.238 1.249 **1.460**]` → `[1.266 1.268 1.258 1.242 1.250 **1.323**]`.
**정상 투하 5건은 원래 y≈1.25 였고, 사고는 6번째 한 건뿐이다.** 가드는
그 이상치만 잘라낸다.

`Watch` 는 감시만 하고 명령을 안 덮는다 — 여기서 정지를 강제하면 부채꼴이

그 상황이다). 침범 판정은 **중심이 앞면을 넘었는가**로 한다. 몸통 원
(`ROBOT_RADIUS_PIECE_M` 8cm)으로 재면 팔이 상자에 들어가야 하는 정상
동작에서도 3cm 겹쳐서, 그걸 세면 경고가 매번 울려 진짜 사고를 가린다.

시뮬레이터에는 pose 잡음이 없다. ArUco 는 mm 단위로 떨리므로 앞면까지

## 사선 투하 — 09-07에 팀원이 45도로 되돌렸다

**09-07에 쓴 이 절의 결론(75도, 고칠 것 없음)은 낡았다.** 같은 날 팀원이
실기에서 사고를 겪고 문턱을 좁혔다. 지금 값은 이렇다.

| 상수 | 09-06 | **지금(09-07)** | 왜 좁혔나 |
|---|---|---|---|
| `MAX_FACING_ERROR_DEG` | 75° → 85° | **45°** | 게이트가 46.1° 를 통과시켰는데 팔의 `MAX_DROP_YAW_OFFSET_RAD`(45°)를 넘어 `SAFE_300` 보정이 거부되고 무보정 투하 → "바구니에 돌진" |
| `SOUTH_APPROACH_SECTOR_DEG` | 120° | **60°** | 부채꼴 가장자리로 들어오면 팔 보정 한계(±30°)를 넘는다. 첫 룩이 바구니 오른쪽에 떨어졌을 때 필요 보정각이 60.6° — 한계의 2배 |
| `BOX_FACE_YAW_TOLERANCE_DEG` | 45° | **20°** | 팔 한계가 45→60→45→20→30° 로 바뀌는 동안 이 값만 45° 로 남아 있었다. 30~45° 로 정렬돼도 "됐다"고 넘겼는데 팔은 거부 |

즉 **사선 투하 자체는 여전히 설계지만, 허용 폭이 팔의 실제 보정 한계에
맞춰 절반 이하로 좁아졌다.** 근본 원인은 "차량이 어디까지 사선이어도
되는가"를 정하는 Host 상수들이 팔의 `MAX_DROP_YAW_OFFSET_RAD` 변화를
안 따라간 것이다 — 팀원 주석이 그렇게 적고 있다.

⚠️ 팀원 주석에 남아 있는 불일치: `MAX_FACING_ERROR_DEG` 주석은 팔 한계를
**45도**로, `SOUTH_APPROACH_SECTOR_DEG` 주석은 **±30도**로 적고 있다.
둘 중 어느 쪽이 지금 `arm_driver_node.py` 값인지 확인이 필요하다.

| upstream 최신 그대로 | **1.487** (FACE_BOX) | **37 mm** | 6/6 | `[1.265 1.250 1.261 1.253 **1.487** 1.245]` |
| **`box_guard` (기본)** | 1.358 (CARRY_TO_DEST) | **0 mm** | 6/6 | `[1.266 1.268 1.258 1.242 1.250 **1.358**]` |

09-07(3.4cm)보다 오히려 조금 더 깊다. 그리고 이번엔 **PLACE 자체가
y=1.487 에서 시작한다** — 로봇이 상자 사각형 안에 선 채로 투하한다.

### 팀원의 09-07 수정이 이 경로에 안 닿는다

`BOX_APPROACH_MARGIN_M` 을 0.15 → 0.20 → 0.28 로 두 번 올렸다("바구니에
돌진", "queen 넣을 때 부딪힘"). 그런데 그 상수가 만드는 `_box_front_xy`
(`dest_xy`)는 **상자로 갈 때는 주행에 안 쓰인다** — `CARRY_TO_DEST`가
09-05부터 `target_center`(상자 안 (1.350, 1.480))로 몰기 때문이다
(mission.py 1244행).

더 확실한 증거: 0.28 로 늘린 지금 `dest_xy` 는 `(1.35, 1.17)` 이고, 접근
부채꼴 중심에서 **0.310m** 다 — 부채꼴 반경 0.25m **밖**이라 거기서는
게이트가 절대 안 열린다.

    toy    dest_xy=(0.45, 1.17)  부채꼴 열림=False  거리=0.310 (한계 0.25)
    chess  dest_xy=(1.35, 1.17)  부채꼴 열림=False  거리=0.310 (한계 0.25)

즉 이 상수는 지금 `_retreat_for_overhead_reapproach`(바구니를 3회 연속
못 찾았을 때의 재접근)와 `begin_carrying` 에만 걸린다. **정상 접근에서
로봇이 멈추는 자리는 0.15 때와 똑같다.**

### 부채꼴을 좁힌 것이 이 문제를 키운다

`SOUTH_APPROACH_SECTOR_DEG` 가 120° → 60° 로 줄었다. 게이트가 열리는 창이
좁아졌다는 뜻이고, 그동안 로봇은 `target_center`(상자 안)를 향해 계속
전진한다 — **닫혀 있는 시간이 길수록 더 깊이 들어간다.** 재측정에서
침범이 34mm → 37mm 로 늘고 PLACE 시작점이 1.460 → 1.487 로 깊어진 게
그 방향과 맞는다.

## 음성 입력

로컬 Whisper(`faster-whisper`)라 인터넷도 API 키도 필요 없다. 첫 사용 때
모델(base, 약 150 MB)을 한 번 내려받는다. 없으면 마이크 버튼만 조용히
꺼지고 나머지는 정상 동작한다.

```
pip install -r requirements-ui.txt
```

**자동 전송은 안 한다**(사용자 확정 2026-09-07) — 인식 결과를 보여주고
사람이 확인 버튼을 눌러야 나간다. 신뢰도 70% 미만 단어가 있으면 그 단어만
짚어 되묻는다(W-401).

### ⚠️ 기본 입력 장치가 블루투스면 안 열린다

이 맥에서 실측: 기본 입력이 블루투스 헤드셋으로 잡혀 있어
`PaErrorCode -9986` 으로 실패했다. 코드 문제가 아니라 장치 문제다.
내장 마이크를 쓰려면 장치 번호를 지정한다:

```
WHISPER_MIC_DEVICE=2 python run_sim_ui.py      # 번호는 화면 안내에 뜬다
```

마이크가 안 열리면 화면 알림이 **지금 쓸 수 있는 장치 목록을 같이** 보여준다.

## 아직 안 한 것

- ~~화면 push 비용 측정~~ → **끝났다.** `run_mission_ui.py` 를 카메라 1대로
  실제로 돌려 `--hz-every` 로 쟀다:

  ```
  [hz] 30.0 Hz  (33 ms/사이클)  캡처+ArUco 32  geti 0  FSM 0  화면 1 ms
  ```

  화면이 **1–3 ms** 다. 팀 실측의 예전 지도는 같은 자리에서 90 ms 였고
  그게 사이클의 최대 비용이었다 — 이 UI 는 그 자리를 거의 비운다.
  (`geti 0` 은 추론이 배경 스레드라 메인 루프가 안 기다린다는 뜻이지
  추론이 공짜라는 뜻이 아니다. 카메라 2대 + 실제 기물이 있으면 전체
  사이클은 이보다 느려진다 — 다만 **화면 몫은 그대로 1–3 ms** 다.)
- 음성 입력(`voice_input.py`)은 `run_sim_ui.py` 에 안 물려 있다
- `ui/mock.js`(실물 없이 보는 목업 재생)는 옛 상태 이름을 쓴다
